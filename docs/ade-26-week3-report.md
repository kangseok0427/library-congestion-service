# Week 3 개인 중간보고 — 도형준 (ADE-26)

작성일: 2026-09-30. 확인 기준: 이 문서의 코드·테스트 관련 서술은 2026-09-30 이 세션에서 직접
저장소를 확인하고 명령을 실행한 결과다(§1의 pytest/e2e 재실행 등). 과거 기록을 인용한 부분은
그렇게 표시했다. Linear 이슈 상태(Done 등)는 그 자체로 현장 검증이나 배포 완료를 뜻하지
않으므로, 이번에 직접 확인하지 못한 항목은 미확정으로 남긴다.

## 1. 지금까지 실제로 만든 것과 현재 동작 상태

- 이용자 웹 화면(ADE-9/T05, ADE-38/T14): 날짜 선택(KST 기준 오늘~+7일), 지금 혼잡 단계 카드,
  추천 방문 시간, 시간대별 막대그래프+표, 선택 날짜의 실제 집계로 구성되어 있다. 오늘 다시
  `pytest`(159 passed)와 Playwright `scripts.e2e`(PASS, 합성 데이터)를 직접 돌려 모바일
  390px에서 가로 스크롤 없이 동작하는 것까지 재확인했다.
- 혼잡 판정은 과거 같은 시간대 "입장량" 분포의 백분위(35 이하 여유 / 70 이하 보통 / 나머지
  혼잡)로 매긴다. "현재 체류인원이 아니다"라는 안내가 화면에 상시 노출된다.
- 운영시간·휴관일(평일 09~21시, 주말 09~17시, 매주 월요일 + 등록 휴관일)을 별도 정책으로
  분리해 예측·추천·통계에서 제외한다. 다만 **IN_21(21시대) 버킷이 시작 라벨인지 종료 라벨인지는
  아직 현장에서 확인되지 않았다.** Linear ADE-38은 Done 상태지만, 이슈 설명 자체가 이 항목을
  별도 미확인으로 남기고 있어서 이번 보고에서도 확정하지 않는다.
- 다른 팀원 작업(ADE-15/16 baseline forecast, ADE-35 인증 업로드, ADE-37 Windows 업로더,
  ADE-28 배포)도 develop에 병합돼 있다. 이 부분은 이번에 내가 직접 재검증하지 않았고, 과거
  문서(`docs/verification.md` 등)의 기록을 그대로 인용한 것이다.
- 새로 맡은 ADE-41(잔류 인원 기반 그래프)은 선행 작업인 ADE-40(추정 체류 인원 API, 이가영
  담당)이 아직 착수 전이다 — Linear 상태 Todo, `estimated_present` 필드를 저장소 전체
  브랜치에서 검색해도 없음을 오늘 확인했다. 이번에 한 일은 확인·문서화·API 요청 문안
  준비까지고, 화면 코드는 바꾸지 않았다. **ADE-41은 미완료다.**

## 2. 추가하면 좋을 기능과 이유

- 범례에 "자료 부족"(회색) 항목 추가. 지금은 여유/보통/혼잡 3개만 범례에 있는데, 실제 화면에는
  자료가 없을 때 회색 막대가 나온다. 이용자가 회색 막대의 의미를 범례 없이 추측해야 하므로,
  작은 변경으로 일관성을 바로 올릴 수 있다.
- ADE-41이 풀리면(ADE-40 연결 후) 화면의 "추정 체류 인원"이 무엇을 근거로 계산됐는지 짧게
  볼 수 있는 안내(ADE-39 설명자료 연결)를 추가하면 좋겠다. 지금도 "현재 인원이 아님" 안내는
  있지만, 왜 그런지 근거로 이어지는 연결이 없다.

## 3. 제거·축소하면 좋을 기능과 이유

- 유지 제안: 지금 카드 수(지금 상태/추천/시간대별/실제집계 4개)나 화면 구조를 줄일 필요는
  못 느꼈다. 각 카드의 역할이 분명하고, "표로 보기"와 그래프가 같은 정보를 두 번 보여주는 것도
  접근성 검증용으로 의도된 중복(`docs/architecture.md`에 명시)이라 축소 대상은 아니라고 본다.
- 축소 제안: "선택한 날짜의 실제 집계" 섹션은 오늘 이후 날짜를 조회하면 8개 날짜 중 7개에서
  항상 "집계 전"만 보여준다. 미래 날짜에서는 이 섹션을 접어두거나 숨기는 쪽이 정보량 대비
  화면을 덜 차지할 것 같다.

## 4. 품질과 개발 효율을 높일 방법

- API 계약이 확정되기 전에 프론트가 필드명을 먼저 정해버리는 일이 이번에도 반복될 뻔했다
  (ADE-41). 새 백엔드 필드를 추가하는 이슈(ADE-40 같은 경우)는 착수 시점에 필드 위치·null
  규칙 초안을 이슈 본문에 먼저 짧게 적어두면, 뒤에 있는 프론트 작업이 추측 없이 바로 준비될
  수 있을 것 같다.
- Playwright E2E가 합성 데이터로 잘 도는 것은 좋다(오늘도 재실행해서 확인). 다만 검증이
  `scripts/e2e.py` 한 파일에 다 몰려 있어서, 화면 요구사항이 늘어날 때마다 이 파일이 계속
  길어진다. 기능 단위로 나눠두면 나중에 어디가 깨졌는지 찾기 더 쉬울 것 같다.

## 5. 지금까지의 역할 분담·협업·일정에 대한 평가

- ADE-41이 ADE-40에 의존하는 구조 자체는 합리적이다(체류 인원 계산 로직이 먼저 확정돼야
  화면이 그걸 반영할 수 있음). 다만 두 이슈가 같은 Week 3 마일스톤에 잡혀 있는데 ADE-40이
  아직 Todo라서, 이번 주 안에 내 쪽 작업이 실제로 끝나기는 어려운 일정이었다. 누구의 잘못이라기
  보다 선행 이슈 착수 시점이 늦어진 것으로 보인다.
- ADE-39(설명자료)도 이슈 상태는 Todo지만 초안 파일이 이미 첨부돼 있어서, 문서 작업이 이슈
  상태보다 앞서 진행되고 있는 것으로 보인다. 이슈 상태만으로 진행률을 판단하기 어려운
  경우가 있다는 뜻으로 참고했다.

## 6. Week 3 이후 우선순위 제안

1. ADE-40(추정 체류 인원 API) 계약 확정 — 필드 위치, null 규칙, 추천 로직 기준 포함. 이게
   먼저 되어야 ADE-41이 실제로 진행 가능하다.
2. ADE-40 확정 즉시 ADE-41 프론트 반영 + 회귀 테스트.
3. ADE-38의 IN_21 현장 확인 — 계속 미확인 상태로 남아 있어서, 이번에 정리하지 못하면 다음
   보고에도 같은 항목이 반복될 것 같다.
