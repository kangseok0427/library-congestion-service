## 2. 추가하면 좋을 기능

- **ADE-40 계산을 팀 `backend/`로 옮기는 작업**을 별도 이슈로 잡는 것.
  이유: 지금 구조로는 ADE-40이 끝나도 이용자 화면이 바뀌지 않는다. ADE-41의 완료 조건이 이 작업에 걸려 있다.
- **실제 Excel로 "자료 부족" 비율 확인**. ADE-40은 누적값이 음수가 되면 그날 나머지를 추정 불가로 둔다.
  ADE-39 초안에 따르면 OUT이 하루 약 40명 더 많이 세어진다고 해서, 실제 데이터에서는 오후 대부분이
  회색이 될 수도 있다. 화면을 바꾸기 전에 숫자로 확인해야 한다.

## 3. 제거·축소하면 좋을 기능

- **축소: 추정 체류 인원 "숫자" 표시.** ADE-39 초안은 이 값이 음수까지 나오는 추정치라
  숫자 대신 색으로만 보여 주자고 한다. ADE-41 명세는 숫자 표시를 요구해서 지금은 숫자를 보여 주게 구현했지만,
  실데이터 오차가 크면 표의 숫자 칸만 가리고 색과 단계만 남기는 쪽이 이용자 오해를 줄인다고 본다.
  바꾸는 데 드는 작업도 작다. 10/1 토론에서 결정했으면 한다.
- **축소: 미래 날짜의 "실제 집계" 카드.** 8개 조회 날짜 중 오늘을 뺀 날은 항상 "집계 전" 또는 "휴관일"만 나온다.
  미래 날짜에서는 한 줄 안내로 줄이는 편이 화면을 덜 차지한다.
- **유지: 표로 보기.** 막대와 같은 값을 반복하지만 스크린리더와 테스트에서 같은 숫자를 확인하는 기준이 된다.

## 4. 품질과 개발 효율

- **백엔드 변경은 팀 저장소 PR로.** ADE-40이 별도 저장소에서 진행되면서 기존 API 계약(날짜 파라미터,
  운영 달력, KST)이 빠졌고, 완료 알림 후에도 화면 연결이 안 됐다. 팀 저장소 PR이었다면 기존 테스트
  159개가 이 차이를 바로 잡았을 것이다.
- **API 계약을 이슈 본문에 먼저 적기.** 필드 이름, null 규칙, 추천이 없을 때 값(null인지 0인지) 등.
  이번에 팀 백엔드는 null, operator-api는 0을 써서 프론트가 둘 다 처리하게 했다.
- **실제 백엔드 코드로 테스트 픽스처 만들기.** 이번에 operator-api 코드를 직접 돌려 응답을 저장하고 그걸로
  화면을 검증했다. 손으로 만든 가짜 응답보다 계약 차이를 더 잘 드러냈다(추천 시간 문제도 여기서 발견).
